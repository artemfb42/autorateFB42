# Персональний аркуш перевірки SRS 1.0 — Фощій Дмитро

**Продукт:** «АвтоРейт»  
**Роль у команді:** Тест-аналітик  
**Джерело:** [SRS 1.0 «АвтоРейт»](../SRS_05_АвтоРейт.pdf), 6 сторінок.  
**Ділянки незалежної перевірки:** 3 — Функціональні вимоги; 5 — Бізнес-логіка модуля.  
## 1. Рамки та спосіб перевірки

На перший план винесені входи, граничні значення, результати і винятки методів Java 17. Виправлення тут оцінюється за тим, чи зможемо за ним написати однозначний тест-кейс або JUnit-тест.

**Власний акцент:** Контракти даних та майбутня тестованість: валідатор голосу, сортування, пошук і межі обов’язкових даних.

**Підхід:** Для кожної пропозиції визначено набори тестових даних і очікувані результати без припущення, що тести вже виконано.

## 3. Докази, оцінка і пропозиції

**Статус особистого аркуша:** матеріал підготовлено для персональної звірки за SRS 1.0. Запропоновані формулювання представлені в робочій редакції, сумісній із [загальним реєстром](../requirements-defects.md); це не доказ того, що автор незалежно виявив кожну проблему до зведення. Кожен учасник має перевірити первинні докази, підтвердити лише власні фактичні знахідки та відзначити виправлення, що виникли під час спільного опрацювання. Спільне авторство встановлюється тільки після такого підтвердження.

### IA-01 / RD-06 — `F-30`, с. 3

**Критерій / пункт:** Повнота (п. 4, 5)  
**Доказ із SRS 1.0:** Перевіряються обов'язкові поля, пароль та його підтвердження  
**Проблема:** Не визначено правило зайнятого логіна й реакцію системи на повторну реєстрацію з ним.

**Окремий аргумент / контрольний приклад:** Повторна реєстрація з тим самим логіном не має явно заданого результату; перевірити нормалізацію регістру.

**Пропозиція готової редакції:** Логін нового облікового запису має бути унікальним без урахування регістру. Якщо логін уже існує, реєстрація не виконується й показується «Login already exists.».

**Особистий напрямок аналізу:** Випадок дубля логіна слід відділити від вимог до формату пароля; це інший негативний результат реєстрації.

### IA-02 / RD-01 — `F-30`, с. 3

**Критерій / пункт:** Однозначність (п. 2, 4)  
**Доказ із SRS 1.0:** «пароль є достатньо складним»  
**Проблема:** Не визначено мінімальну довжину, допустимі символи та обов'язкові категорії.

**Окремий аргумент / контрольний приклад:** Спробувати паролі 7, 8, 64 і 65 символів, а також рядки без цифр/без літер; межі є пропозицією, не даними оригіналу.

**Пропозиція готової редакції:** Пароль містить 8–64 символи, щонайменше одну літеру й одну цифру. За порушення правила реєстрація відхиляється з повідомленням «Password must be 8-64 characters and include a letter and a digit.». Запропоновані межі потребують погодження.

**Особистий напрямок аналізу:** Числові межі 8 і 64 створюють перевірювані межові значення, але тільки після підтвердження власником вимог.

### IA-03 / RD-14 — `F-70 / F-120`, с. 3–4

**Критерій / пункт:** Простежуваність (п. 1, 5)  
**Доказ із SRS 1.0:** F-120 дублює опис перегляду списку моделей із F-70  
**Проблема:** Одна функція описана двома вимогами.

**Окремий аргумент / контрольний приклад:** F-120 повторює сценарій F-70, що створює два ID для однієї функції; не зрушувати інші ідентифікатори.

**Пропозиція готової редакції:** Вилучити F-120 як дубль F-70. ID F-120 залишити зарезервованим, інші ID не перенумеровувати.

**Особистий напрямок аналізу:** Видалення дубля F-120 має лишити історію ID у журналі змін; автоматичне перенумерування зламає посилання.

### IA-04 / RD-17 — `F-110`, с. 4

**Критерій / пункт:** Здійсненність (п. 1)  
**Доказ із SRS 1.0:** «автоматично перевіряє достовірність ... за державними реєстрами»  
**Проблема:** Не визначені доступні інтеграції, права й ресурси для перевірки державних реєстрів.

**Окремий аргумент / контрольний приклад:** За SRS немає опису доступу до державних реєстрів, контрактів API й правових підстав; локальна валідація — альтернативна вимога.

**Пропозиція готової редакції:** Замість зовнішньої перевірки використовувати локальну валідацію: Age — ціле число 0–120; Phone — 8–15 цифр із необов'язковим початковим «+»; Address — 1–200 непорожніх символів після видалення крайніх пробілів. За помилки не зберігати дані та показувати повідомлення біля відповідного поля. Узгоджено з GUI-45: поле «Age» приймає лише цілі числа від 0 до 120. Межі погоджуються із замовником.

**Особистий напрямок аналізу:** Виклик держреєстрів немає чим замінити в юніт-тестах без контракту; запропонована локальна валідація є зміною обсягу функції.

**Примітка:** запропоновані нові числові межі або текст повідомлення потребують підтвердження замовником.

### IA-05 / RD-09 — `F-90 / BL-50`, с. 3, 5

**Критерій / пункт:** Несуперечливість (п. 2)  
**Доказ із SRS 1.0:** F-90 не дозволяє голос без коментаря; BL-50 дозволяє порожній коментар або null  
**Проблема:** Правила вебзастосунку та Java-модуля не збігаються.

**Окремий аргумент / контрольний приклад:** Порівняти вхід Comment у браузері й передавання null/""/пробілів до VoteValidator; обидва шари мають діяти однаково.

**Пропозиція готової редакції:** У BL-50 визначити: після видалення крайніх пробілів коментар має містити 1–200 символів Unicode. Порожній, null або пробільний коментар відхиляється з повідомленням «коментар обов'язковий». Довший за 200 символів — «коментар задовгий».

**Особистий напрямок аналізу:** Вхідні значення null і порожній рядок мають давати однакову зрозумілу помилку на рівні валідатора голосу.

### IA-06 / RD-16 — `F-100`, с. 3

**Критерій / пункт:** Повнота (п. 3)  
**Доказ із SRS 1.0:** «правило BL-35»  
**Проблема:** Посилання веде на відсутню вимогу BL-35.

**Окремий аргумент / контрольний приклад:** Знайти BL-35 у розділі 5 неможливо; для правила «один користувач — один голос на модель» існує BL-30.

**Пропозиція готової редакції:** Замінити посилання на `BL-30`, яка визначає один голос користувача за модель та відхилення повторного голосу.

**Особистий напрямок аналізу:** У JUnit набір перевірок повторного голосу слід пов’язати з BL-30, а не з неіснуючим BL-35.

### IA-07 / RD-10 — `F-130 / BL-20`, с. 4–5

**Критерій / пункт:** Несуперечливість (п. 2)  
**Доказ із SRS 1.0:** F-130: щонайменше 5 голосів; BL-20: щонайменше 3  
**Проблема:** Вимоги містять різні пороги для включення моделі до рейтингу.

**Окремий аргумент / контрольний приклад:** Порівняти моделі з 2, 3, 4 і 5 голосами; між F-130 та BL-20 немає єдиного очікуваного набору.

**Пропозиція готової редакції:** Узгодити єдиний поріг. Запропоновано 3 голоси для F-130 та BL-20. Остаточне значення визначає замовник.

**Особистий напрямок аналізу:** Для порогу 3/5 необхідно підготувати фікстури з 2–5 голосами, не спираючись на живі лічильники загального демостенда.

**Примітка:** запропоновані нові числові межі або текст повідомлення потребують підтвердження замовником.

### IA-08 / RD-25 — Розділ 1.3, `F-60 / F-130`, с. 2–4

**Критерій / пункт:** Несуперечливість (п. 2)  
**Доказ із SRS 1.0:** У глосарії та F-60 ранг 1 має модель з найбільшою кількістю голосів; F-130 визначає ранг за спаданням рейтингу  
**Проблема:** Кількість голосів і зважений рейтинг можуть давати різне ранжування.

**Окремий аргумент / контрольний приклад:** Сконструювати дві моделі: більше голосів, але менший weighted rating; два правила дадуть різні Rank.

**Пропозиція готової редакції:** Ранг визначається за спаданням зваженого рейтингу BL-10. За рівності застосовується правило BL-20. Популярність марки й моделі за F-10 визначається окремо — кількістю зарахованих голосів.

**Особистий напрямок аналізу:** Порядок за Votes і за Rating математично різний; для тестування необхідні два набори з різним рейтингом і кількістю голосів.

### IA-09 / RD-07 — `BL-70`, с. 5

**Критерій / пункт:** Повнота (п. 1, 5)  
**Доказ із SRS 1.0:** «упорядкованих за рейтингом за спаданням»  
**Проблема:** Не визначено порядок моделей з однаковим рейтингом.

**Окремий аргумент / контрольний приклад:** Різний порядок однакових рейтингів у вхідному списку може давати різний вихід; перевірити алфавітний tie-break та незмінність входу.

**Пропозиція готової редакції:** `ModelSearch.sortByRating(models)` повертає новий список за спаданням рейтингу. За рівності рейтингу сортує за повною назвою «марка + модель» в алфавітному порядку без урахування регістру. Вхідний список не змінюється.

**Особистий напрямок аналізу:** Важливо перевірити як порядок рівних оцінок, так і той факт, що sortByRating не змінює переданий список.

### IA-10 / RD-18 — `BL-60`, с. 5

**Критерій / пункт:** Здійсненність (п. 1)  
**Доказ із SRS 1.0:** Пошук має розпізнавати «будь-яку мову світу» та «саме ту модель, яку мав на увазі користувач»  
**Проблема:** Гарантоване розпізнавання довільної мови, помилки та наміру недосяжне в межах визначеного модуля.

**Окремий аргумент / контрольний приклад:** Префіксний пошук — визначена функція, а вгадування наміру за довільною мовою — недосяжна абсолютна гарантія.

**Пропозиція готової редакції:** `ModelSearch.search(query, models)` шукає за префіксом назви марки або моделі без урахування регістру. Порожній чи пробільний запит повертає порожній список. Порядок результатів зберігає порядок вхідного списку. Гарантії розпізнавання всіх мов та помилок вилучаються.

**Особистий напрямок аналізу:** Шукати префікс у двох полях можна строго протестувати; «здогадуватися намір» у довільній мові — не визначений алгоритм.

### IA-11 / RD-03 — `BL-80`, с. 5

**Критерій / пункт:** Однозначність (п. 4, 5)  
**Доказ із SRS 1.0:** «окреме слово зі стоп-списку»  
**Проблема:** Не визначено межу слова для пунктуації, цифр та Unicode.

**Окремий аргумент / контрольний приклад:** Пари "spam"/"spammer" і "spam!"/"SpAm" мають дозволяти однозначне розділення на токени.

**Пропозиція готової редакції:** Коментар розбивається на токени за символами, які не є літерами або цифрами Unicode. Зі стоп-списком порівнюються цілі токени без урахування регістру. «spam» відхиляється, «spammer» не вважається збігом зі словом «spam».

**Особистий напрямок аналізу:** Токенізація за Unicode змінює поведінку на межах слова; у тестових даних слід мати літери, цифри, пунктуацію та різний регістр.

### IA-12 / RD-24 — `BL-80`, с. 5

**Критерій / пункт:** Тестопридатність (п. 1)  
**Доказ із SRS 1.0:** «Модуль загалом має працювати без помилок за будь-яких вхідних даних»  
**Проблема:** Абсолютна неперевірювана вимога без умов проходження/непроходження.

**Окремий аргумент / контрольний приклад:** Один універсальний тест не доведе «без помилок за будь-яких даних»; потрібен скінченний набір контрактів для методів.

**Пропозиція готової редакції:** Вилучити загальну гарантію. Для методів модуля визначити конкретні контракти: null замість обов'язкової колекції спричиняє IllegalArgumentException; невалідні rating/reputation обробляються за BL-10 та BL-40; порушення правил голосування повертають відповідні повідомлення BL-30, BL-50 і BL-80.

**Особистий напрямок аналізу:** Повний контракт методів RatingAggregator/VoteValidator/ModelSearch дозволить перевіряти винятки і повідомлення окремо, а не вимагати абсолютної безпомилковості.

## 4. Питання поза затвердженим реєстром

Для ModelSearch.search не задано окрему поведінку за null у параметрі query; загальне правило про null стосується колекцій. Запропоновано винести випадок null-query на уточнення контракту перед спринтом 4. У поточні RD-01…RD-28 питання не додавати без погодження.
