# Персональний аркуш перевірки SRS 1.0 — Деркач Юрій

**Продукт:** «АвтоРейт»  
**Роль у команді:** Керівник тестування  
**Джерело:** [SRS 1.0 «АвтоРейт»](../SRS_05_АвтоРейт.pdf), 6 сторінок.  
**Ділянки незалежної перевірки:** 1 — Вступ; 3 — Функціональні вимоги; 6 — Нефункціональні вимоги.  

## 1. Рамки та спосіб перевірки

Окремо аналізую суперечності між сценаріями: чи може команда однозначно пояснити замовникові, що вважатиметься успішною реєстрацією, входом, рейтингом і завершенням сеансу.

**Власний акцент:** Наскрізна логіка продукту: від значення терміна в глосарії до поведінки сторінок, голосування й експлуатаційних гарантій.

**Підхід:** Звірка формулювань між розділами, побудова сценаріїв користувача та підготовка питань, які змінюють пріоритети тест-плану.

## 3. Докази, оцінка і пропозиції

**Статус особистого аркуша:** матеріал підготовлено для персональної звірки за SRS 1.0. Запропоновані формулювання представлені в робочій редакції, сумісній із [загальним реєстром](../requirements-defects.md); це не доказ того, що автор незалежно виявив кожну проблему до зведення. Кожен учасник має перевірити первинні докази, підтвердити лише власні фактичні знахідки та відзначити виправлення, що виникли під час спільного опрацювання. Спільне авторство встановлюється тільки після такого підтвердження.

### IA-01 / RD-28 — `F-10`, с. 3

**Критерій / пункт:** Однозначність (п. 1, 4)  
**Доказ із SRS 1.0:** Блоки «Popular Make» і «Popular Model»  
**Проблема:** Визначено інформацію в блоках, але не правило вибору популярної марки чи моделі та порядок за рівності голосів.

**Окремий аргумент / контрольний приклад:** Взяти два об’єкти з однаковим числом голосів; правило F-10 не встановлює, який показати першим. Обраний tie-breaker потрібно погодити.

**Пропозиція готової редакції:** «Popular Make» — марка з найбільшою сумою зарахованих голосів за всі її моделі. «Popular Model» — модель із найбільшою кількістю зарахованих голосів. За рівності застосовується алфавітний порядок без урахування регістру: для марки — за назвою марки, для моделі — за повною назвою «марка + модель». Популярність не ототожнюється зі зваженим рейтингом BL-10.

**Особистий напрямок аналізу:** За однакового лічильника голосів потрібно визначити порядок вибору Popular Make/Model; інакше різні дані каталогу дають непередбачуваний результат демонстрації.

**Примітка:** запропоновані нові числові межі або текст повідомлення потребують підтвердження замовником.

### IA-02 / RD-04 — `F-20`, с. 3

**Критерій / пункт:** Однозначність (п. 1, 4)  
**Доказ із SRS 1.0:** «повідомлення про успішне створення облікового запису»  
**Проблема:** Не визначено конкретного повідомлення, яке має побачити користувач.

**Окремий аргумент / контрольний приклад:** Порівняти повідомлення після Register із точним рядком у прийнятій SRS. Без повідомлення-еталона результат не визначений.

**Пропозиція готової редакції:** Після успішної реєстрації система показує «Registration successful.» та очищує форму. Cancel повертає на головну сторінку без збереження введених даних. Текст повідомлення потребує погодження.

**Особистий напрямок аналізу:** Після успішної реєстрації користувач має бачити єдине контрольне повідомлення; до його погодження тест не повинен прив’язуватися до довільного тексту.

**Примітка:** запропоновані нові числові межі або текст повідомлення потребують підтвердження замовником.

### IA-03 / RD-01 — `F-30`, с. 3

**Критерій / пункт:** Однозначність (п. 2, 4)  
**Доказ із SRS 1.0:** «пароль є достатньо складним»  
**Проблема:** Не визначено мінімальну довжину, допустимі символи та обов'язкові категорії.

**Окремий аргумент / контрольний приклад:** Спробувати паролі 7, 8, 64 і 65 символів, а також рядки без цифр/без літер; межі є пропозицією, не даними оригіналу.

**Пропозиція готової редакції:** Пароль містить 8–64 символи, щонайменше одну літеру й одну цифру. За порушення правила реєстрація відхиляється з повідомленням «Password must be 8-64 characters and include a letter and a digit.». Запропоновані межі потребують погодження.

**Особистий напрямок аналізу:** Парольна політика впливає на реєстрацію та сценарії входу; до затвердження треба пояснити команді, які дані вважати валідними.

### IA-04 / RD-05 — `F-40`, с. 3

**Критерій / пункт:** Повнота (п. 4, 5)  
**Доказ із SRS 1.0:** Описано успішний вхід  
**Проблема:** Немає реакції системи на неправильний логін або пароль.

**Окремий аргумент / контрольний приклад:** Для хибної пари login/password зафіксувати: неавторизований стан, збереження поточної сторінки, місце повідомлення.

**Пропозиція готової редакції:** За неправильних облікових даних сеанс не створюється, користувач залишається на поточній сторінці, поруч із формою показується «Invalid login or password.». Повідомлення зникає після зміни даних, оновлення сторінки або наступного успішного входу відповідно до GUI-30 та U-20.

**Особистий напрямок аналізу:** Вимога описує тільки успішний вхід, хоча негативний сценарій є критичним для того, щоб не створювати сеанс після помилки.

### IA-05 / RD-16 — `F-100`, с. 3

**Критерій / пункт:** Повнота (п. 3)  
**Доказ із SRS 1.0:** «правило BL-35»  
**Проблема:** Посилання веде на відсутню вимогу BL-35.

**Окремий аргумент / контрольний приклад:** Знайти BL-35 у розділі 5 неможливо; для правила «один користувач — один голос на модель» існує BL-30.

**Пропозиція готової редакції:** Замінити посилання на `BL-30`, яка визначає один голос користувача за модель та відхилення повторного голосу.

**Особистий напрямок аналізу:** Правильний BL-30 потрібен не тільки для реалізації, а й для матриці трасування до майбутнього тест-кейсу повторного голосу.

### IA-06 / RD-09 — `F-90 / BL-50`, с. 3, 5

**Критерій / пункт:** Несуперечливість (п. 2)  
**Доказ із SRS 1.0:** F-90 не дозволяє голос без коментаря; BL-50 дозволяє порожній коментар або null  
**Проблема:** Правила вебзастосунку та Java-модуля не збігаються.

**Окремий аргумент / контрольний приклад:** Порівняти вхід Comment у браузері й передавання null/""/пробілів до VoteValidator; обидва шари мають діяти однаково.

**Пропозиція готової редакції:** У BL-50 визначити: після видалення крайніх пробілів коментар має містити 1–200 символів Unicode. Порожній, null або пробільний коментар відхиляється з повідомленням «коментар обов'язковий». Довший за 200 символів — «коментар задовгий».

**Особистий напрямок аналізу:** Той самий користувацький сценарій може пройти форму та бути відхилений Java-модулем або навпаки; варіант правила має бути один.

### IA-07 / RD-10 — `F-130 / BL-20`, с. 4–5

**Критерій / пункт:** Несуперечливість (п. 2)  
**Доказ із SRS 1.0:** F-130: щонайменше 5 голосів; BL-20: щонайменше 3  
**Проблема:** Вимоги містять різні пороги для включення моделі до рейтингу.

**Окремий аргумент / контрольний приклад:** Порівняти моделі з 2, 3, 4 і 5 голосами; між F-130 та BL-20 немає єдиного очікуваного набору.

**Пропозиція готової редакції:** Узгодити єдиний поріг. Запропоновано 3 голоси для F-130 та BL-20. Остаточне значення визначає замовник.

**Особистий напрямок аналізу:** Рішення про мінімум голосів має прийняти замовник: QA не може вибрати бізнес-поріг лише тому, що одна вимога розташована пізніше.

**Примітка:** запропоновані нові числові межі або текст повідомлення потребують підтвердження замовником.

### IA-08 / RD-11 — `F-140 / GUI-60`, с. 4

**Критерій / пункт:** Несуперечливість (п. 2)  
**Доказ із SRS 1.0:** F-140: 5 рядків; GUI-60: 10 рядків  
**Проблема:** Суперечлива кількість записів на сторінці таблиці.

**Окремий аргумент / контрольний приклад:** Для 11 моделей перевірити кількість рядків на сторінках, стан кнопок і «page X of Y»; F і GUI дають несумісні числа.

**Пропозиція готової редакції:** У GUI-60 встановити 5 рядків, відповідно до F-140. Кнопки попередньої та наступної сторінки і напис «page X of Y» розміщуються під таблицею по центру.

**Особистий напрямок аналізу:** На демо можна показати відмінність на 11 записах, але до погодження числа 5/10 проходження тесту не визначене.

### IA-09 / RD-26 — `F-10 / F-60 / F-70 / F-130`, с. 3–4

**Критерій / пункт:** Несуперечливість (п. 2)  
**Доказ із SRS 1.0:** F-10 і F-70 говорять про всі зареєстровані моделі; F-130 дозволяє включати до загального рейтингу тільки моделі з мінімальною кількістю голосів  
**Проблема:** Неузгоджений склад загального рейтингу. Для таблиці марки також не визначено порядок моделей без рангу.

**Окремий аргумент / контрольний приклад:** У F-70 потрібне правило для моделей, що не пройшли поріг F-130; список «усіх» несумісний із включенням лише ранжованих.

**Пропозиція готової редакції:** У F-10 для Overall Rating використовувати «List of ranked models.». У F-70 відображати лише моделі, які відповідають порогу F-130. У F-60 показувати всі моделі марки: спочатку ранжовані за зростанням Rank, потім моделі без рангу зі значенням «—» в алфавітному порядку. Запропонований поріг — 3 голоси, потребує погодження замовником.

**Особистий напрямок аналізу:** Для Overall Rating необхідно окремо визначити, що робити з моделями без Rank; інакше некоректні дані сприйматимуться як дефект сортування.

### IA-10 / RD-12 — `S-20`, с. 6

**Критерій / пункт:** Несуперечливість (п. 1)  
**Доказ із SRS 1.0:** «Сеанс користувача зберігається безстроково» та «після 30 хвилин неактивності сеанс автоматично завершується»  
**Проблема:** Дві умови суперечать одна одній.

**Окремий аргумент / контрольний приклад:** Неможливо одночасно виконати «безстроково» та «30 хв неактивності» у буквальному сенсі; уточнити, що має перевагу.

**Пропозиція готової редакції:** Сеанс завершується після Logout або 30 хвилин відсутності активності. Після завершення сеансу для профілю і голосування потрібен повторний вхід.

**Особистий напрямок аналізу:** Обмеження сеансу впливає на доступ до Profile та Vote; у сценарії виходу треба розрізнити бездіяльність і натискання Logout.

### IA-11 / RD-19 — `P-10`, с. 5–6

**Критерій / пункт:** Здійсненність (п. 1)  
**Доказ із SRS 1.0:** «не довше ніж за 50 мс ... включно з мобільним 2G»  
**Проблема:** Неможливо гарантувати цей час за будь-якого з'єднання та обсягу даних.

**Окремий аргумент / контрольний приклад:** Реальний час 2G визначається не тільки кодом SPA: неможливо гарантувати 50 мс за будь-якого з’єднання.

**Пропозиція готової редакції:** На контрольованому середовищі з каталогом 1000 моделей, мережею 10 Мбіт/с та Chrome 95-й перцентиль часу повного завантаження Overall Rating за 30 вимірюваннями не перевищує 3 с. Значення та умови потребують погодження.

**Особистий напрямок аналізу:** Гарантія для невідомої мережі підміняє властивість програми станом зовнішнього каналу; вимірювати потрібно на зазначеному середовищі.

**Примітка:** запропоновані нові числові межі або текст повідомлення потребують підтвердження замовником.

### IA-12 / RD-08 — `D-10`, с. 6

**Критерій / пункт:** Повнота (п. 3)  
**Доказ із SRS 1.0:** «АР-СТД-07»  
**Проблема:** Специфікація посилається на стандарт документації, якого немає серед переданих матеріалів.

**Окремий аргумент / контрольний приклад:** До виконання вимоги потрібна копія АР-СТД-07; якщо стандарт не надано, немає перевірюваного опису оформлення.

**Пропозиція готової редакції:** Надати стандарт «АР-СТД-07» або замінити посилання самодостатніми вимогами: довідка має містити призначення, реєстрацію, вхід, вихід, пошук, голосування, профіль, помилки та контакти підтримки; для кожного розділу передбачити інструкції й приклади.

**Особистий напрямок аналізу:** Перевіряти документ проти ненаданого стандарту неможливо; перший крок керівника — витребувати його або погодити мінімальний склад довідки.
## 4. Питання поза затвердженим реєстром

Для S-20 потрібно уточнити, які дії рахуються активністю: запит API, натискання миші, перехід між сторінками чи лише автентифіковані операції. Цього SRS 1.0 не визначає. Це питання для замовника, а не окремий затверджений RD.

Цей пункт **не є новим затвердженим дефектом** і не змінює кількість 28 RD; його треба окремо обговорити перед внесенням у реєстр.

## 5. Питання замовнику та команді

- Чи належить модель без мінімуму голосів до Overall Rating?
- Чи надасть замовник стандарт АР-СТД-07?

## 6. Персональна звірка перед підтвердженням авторства

- [ ] Прочитано оригінальні формулювання у призначених розділах SRS 1.0.
- [ ] Для кожної знахідки перевірено цитату, ID, сторінку та відповідність пункту чек-листа.
- [ ] Перевірено всі шість критеріїв для кожного призначеного розділу, навіть якщо дефект не знайдено.
- [ ] Усі числові або нові бізнес-правила позначено як пропозиції, якщо їх немає в SRS 1.0.
- [ ] Особисто підтверджені знахідки передано тест-аналітику для встановлення фактичного авторства.
- [ ] Розбіжні трактування передано на командне обговорення, а не самостійно затверджено.
