## 1. Продукт і межі тестування

### 1.1. Опис продукту

«АвтоРейт» — вебкаталог автомобільних марок і моделей із функціями реєстрації, авторизації, перегляду каталогу, голосування, коментування та роботи з профілем.

Продукт містить дві складові:

1. **Вебзастосунок (SPA):** головна сторінка, реєстрація, вхід, сторінки марок і моделей, голосування, профіль та загальний рейтинг.
2. **Java-модуль `autorate-module`:** агрегація рейтингів, перевірка голосів, пошук і сортування моделей.

У SRS 1.0 визначені класи:

- `RatingAggregator`
- `VoteValidator`
- `ModelSearch`

Модуль використовує Java 17, Maven 3.9 та JUnit 5.

Згідно з SRS 1.0, до поточного обсягу не належать:

- Інтерфейс модерації коментарів.

Водночас правила перевірки коментарів, описані в BL-50 і BL-80, залишаються об'єктами тестування Java-модуля.

## 3. Двадцять чотири типи тестування

### 3.1. Позначення застосовності

- **Так** — для типу є доступні зараз перевірки на demo або наявних документах.
- **Умовно** — тип релевантний продукту, але його повне виконання потребує Java-модуля, окремого стенда чи іншого ресурсу.
- **Ні** — тип не відповідає поточному обсягу або архітектурі продукту.

Статус «Так» не означає, що відповідний тест уже проведено.

### 5.2. Тестові дані

Для Java-модуля передбачити:

- Оцінки: 0, 1, 2, 5, 6.
- Репутацію: 0, 1, 2, 3, 4.
- Кількість голосів: 0, 1, 2, 3, 4, 5.
- Повторні пари `userId` / `modelId`.
- Коментарі довжиною 0, 1, 200, 201 символ.
- Коментарі з пробілів та `null`.
- Стоп-слова: `spam`, `scam`, `casino`, `казино`.
- Рядки Unicode з українськими літерами й емодзі.
- Пошукові запити: порожній, пробільний, префікс у різному регістрі, відсутній префікс.
- Набори моделей: 0, 1, 100, 1000.
- Значення `n` для topN: -1, 0, 1, 100.

### 5.3. Приклад контролю рейтингу

Для двох голосів:

- Голос 1: rating = 5, reputation = 3.
- Голос 2: rating = 1, reputation = 1.

Очікуваний зважений рейтинг:

`(5 × 3 + 1 × 1) / (3 + 1) = 4.0`

Цей приклад використовується для перевірки BL-10 після отримання Java-модуля.

### 5.4. Обмеження публічного demo

Публічні дані можуть змінюватися іншими користувачами. Тому:

- Не перевіряти точну глобальну кількість голосів як незмінну константу.
- Не створювати масово облікові записи.
- Не проводити навантаження або перебір паролів.
- Не змінювати дані інших користувачів.
- Використовувати тільки власні дозволені тестові облікові записи.

## 6. Ризики, припущення та критерії готовності

### 6.1. Ризики виконання тестування

| Ризик | Наслідок | Дії |
|---|---|---|
| SRS 1.1 містить неузгоджені рішення | Неоднозначний очікуваний результат тестів | До фіналізації тест-кейсів Sprint 3 отримати рішення замовника й використовувати затверджену SRS 1.1 |
| Не отримано Java-модуль | Не можна запустити модульні, об'ємні та JVM-тести | Передбачити виконання у Sprint 4 після отримання коду |
| Немає ізольованого вебстенда | Неможливі повноцінні load, stress, recovery та race-тести | Позначити їх умовними й погодити окреме середовище |
| Спільні дані public demo | Нестабільні глобальні лічильники | Перевіряти власну дію та стан інтерфейсу |
| Не визначено джерело rating і reputation у вебголосуванні | Невідомий контракт інтеграції | Поставити питання замовнику; перевірити можливий RD-29 |
| Немає еталона продуктивності | Неможливо виконати справжній benchmarking | Спочатку сформувати базові вимірювання, потім порівняти з еталоном |

### 6.2. Вхідні критерії

Для виконання конкретного тесту мають бути доступні:

1. Чинна версія вимог.
2. Узгоджений очікуваний результат.
3. Тестове середовище.
4. Тестові дані.
5. Необхідні дозволи.
6. Інструменти виконання.

Якщо умова не виконана, тест позначається як заблокований або відкладений.

### 6.3. Критерії завершення

Для кожного виконаного тесту необхідно зафіксувати:

- Ідентифікатор тесту.
- Версію продукту.
- Дату виконання.
- Тестові дані.
- Очікуваний результат.
- Фактичний результат.
- Статус Pass / Fail / Blocked.
- Посилання на дефект за потреби.
